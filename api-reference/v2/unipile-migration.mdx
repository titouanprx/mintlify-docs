LinkupAPI serves the Unipile v1 API: same routes, parameters, responses, errors, pagination and webhook payloads. You change the base URL and the API key; your code stays the same.

<Note>
  The Unipile-compatible API is enabled per workspace. Ask [support@linkupapi.com](mailto:support@linkupapi.com) to turn it on. Until then, every call answers `403 errors/feature_not_subscribed`.
</Note>

## How it works

This is the full migration, where LinkupAPI handles the switch. To keep Unipile for good next to LinkupAPI, see [Keep Unipile alongside](#keep-unipile-alongside).

1. **Your code talks to LinkupAPI only.** You switch the base URL and the key once, for all accounts.
2. **LinkupAPI is connected to your Unipile workspace.** Accounts you haven't moved yet are still served by Unipile, through LinkupAPI. Nothing stops on switch day.
3. **Each account moves when it reconnects.** A LinkedIn session can't be copied from Unipile, so each account logs in once on LinkupAPI. It keeps its `account_id`, its chat ids and its attendee ids.
4. **The Unipile copy is then deleted**, so no message or webhook is sent twice.

## Choose your migration

| Migration | What happens | Steps |
|---|---|---|
| **All accounts, at your pace** (recommended) | Everything keeps working from day one. Accounts move one by one as their users reconnect. | [1](#step-1-point-your-code-at-linkupapi), [2](#step-2-link-your-unipile-workspace), [3](#step-3-move-your-accounts), [4](#step-4-finish), [example](#example-a-full-migration-in-one-week) |
| **Keep Unipile alongside** | You use both APIs side by side, and choose for each account where it connects. No link between them. | [Keep Unipile alongside](#keep-unipile-alongside) |
| **Fresh start** | No link to Unipile. All accounts connect again on LinkupAPI, with new ids. | [1](#step-1-point-your-code-at-linkupapi), then connect accounts as usual |

## Step 1: Point your code at LinkupAPI

| | Unipile | LinkupAPI |
|---|---|---|
| Base URL | `https://{YOUR_DSN}` | `https://api.linkupapi.com/compat` |
| Routes | `/api/v1/...` | `/api/v1/...` (unchanged) |
| Header | `X-API-KEY: <Unipile token>` | `X-API-KEY: <LinkupAPI API key>` |

```bash
curl https://api.linkupapi.com/compat/api/v1/accounts \
  -H "X-API-KEY: YOUR_LINKUPAPI_API_KEY"
```

With the Unipile Node SDK, pass the LinkupAPI base URL as the DSN:

```js
const client = new UnipileClient("https://api.linkupapi.com/compat", "YOUR_LINKUPAPI_API_KEY");
```

Your API key is in the [dashboard](https://app.linkupapi.com). Scoped API keys work the same way.

## Step 2: Link your Unipile workspace

One call, with your Unipile DSN and key:

```bash
curl -X POST https://api.linkupapi.com/compat/api/v1/migration/unipile \
  -H "X-API-KEY: YOUR_LINKUPAPI_API_KEY" -H "Content-Type: application/json" \
  -d '{"dsn": "api8.unipile.com:13851", "api_key": "<your Unipile API key>"}'
```

What this does:

- **Accounts still at Unipile keep working.** Requests on them are sent on to your Unipile workspace and answered as before. `GET /accounts`, and `GET /chats`, `/messages`, `/chat_attendees` without `account_id`, list both sides.
- **Your webhooks are copied** from Unipile (same URL, source, events, headers, accounts). Webhooks you create or delete afterwards are mirrored at Unipile while the link exists.

Your Unipile key is stored encrypted and only sent to your Unipile DSN. New accounts are created on LinkupAPI.

## Step 3: Move your accounts

Reconnect each account **under its Unipile `account_id`**, exactly as you reconnect an account on Unipile:

- Hosted link: `POST /api/v1/hosted/accounts/link` with `type: "reconnect"` and `reconnect_account: "<Unipile account_id>"`.
- Native: `POST /api/v1/accounts/{Unipile account_id}` with the credentials.

As soon as the account is connected on LinkupAPI:

- it keeps its `account_id`;
- its chats and chat attendees keep their ids: the `chat_id` and `attendee_id` you stored from Unipile keep working, in requests, responses and webhooks;
- it is deleted from your Unipile workspace, only if it is the same LinkedIn member, phone number or mailbox.

A new account (`type: "create"` or `POST /api/v1/accounts`) is created on LinkupAPI with a new id, as on Unipile.

## Step 4: Finish

`GET /api/v1/migration/unipile` shows the progress: accounts moved, accounts still at Unipile. It also copies webhooks you created at Unipile in the meantime.

When no account is left at Unipile, remove the link:

```bash
curl -X DELETE https://api.linkupapi.com/compat/api/v1/migration/unipile \
  -H "X-API-KEY: YOUR_LINKUPAPI_API_KEY"
```

## Example: a full migration in one week

| When | You | Your users and campaigns |
|---|---|---|
| Day 1 | Switch the base URL and key, link Unipile. | Nothing changes: every account runs through Unipile. |
| Day 1 | Email each user a reconnect link (hosted link, `type: "reconnect"`, their Unipile `account_id`), to use within the week. | |
| During the week | Nothing. | Each account moves when its user reconnects, with the same ids. Campaigns keep running, on LinkupAPI for moved accounts and on Unipile for the others. |
| End of the week | Check `GET /api/v1/migration/unipile`, remind users who haven't reconnected. | Accounts not moved keep running on Unipile until they reconnect. |
| When all have moved | Unlink Unipile. | |

No account is lost and no campaign stops.

## Keep Unipile alongside

To keep some accounts on Unipile for good, use both APIs side by side. Nothing to link: keep your Unipile client for accounts on Unipile, and add a LinkupAPI client for accounts on LinkupAPI. The routes and payloads are the same, so the same code serves both.

```js
const unipile = new UnipileClient("https://{YOUR_DSN}", "YOUR_UNIPILE_TOKEN");
const linkup = new UnipileClient("https://api.linkupapi.com/compat", "YOUR_LINKUPAPI_API_KEY");
const client = (account) => (account.provider === "linkupapi" ? linkup : unipile);
```

- **You choose where each account connects**: create its hosted link (or native connection) with one client or the other, and store which one with the account.
- **Webhooks**: create the same webhook on both sides. Payloads are identical, so one handler receives both.
- **Moving an account later**: connect it on LinkupAPI (it gets a new `account_id`), then delete it on Unipile.

## Webhook events

Payloads match Unipile's, field for field. Supported sources and events:

| Source | Events |
|---|---|
| `messaging` | `message_received`, `message_read`, `message_reaction`, `message_edited`, `message_deleted`, `message_delivered` |
| `users` | `new_relation` |
| `account_status` | `ok`, `credentials`, `creation_success`, `reconnected`, `deleted` |
| `email` | `mail_received`, `mail_sent` |

## What differs

- **Message ids** of messages from before the move change (chat and attendee ids don't): a message id stored from Unipile no longer resolves. Messages received after the move have stable ids.
- **`GET /api/v1/messages`** (every message of an account) is available a few minutes after the account connects.
- **Filters LinkedIn has removed** are accepted and have no effect, as on Unipile, since LinkedIn itself no longer applies them. Your requests don't fail on them: job `benefits`, `minimum_salary`, `commitments`, `fair_chance_employer`, `location_within_area`; people `open_to`; classic company `industry`, `has_job_offers`, `network_distance`; Sales Nav `technologies`, `mentionned_in_news`; Recruiter `location_within_area` (LinkedIn only applies a radius to postal codes).
- **Anything not supported** answers `501 errors/feature_not_implemented`, with the parameter or route in `detail`. A request is never run with a filter silently dropped.

## Coverage

**Providers:** LinkedIn (classic, Sales Nav, Recruiter Lite), WhatsApp, Gmail, Outlook, IMAP.

| Area | Supported |
|---|---|
| Accounts | Connect, reconnect, hosted links, checkpoints, list, get, delete, restart, proxy |
| Messaging | Chats, messages, attachments, reactions, attendees, InMail (classic, Sales Nav, Recruiter), group chats, mute, archive, delete |
| Users | Profiles, own profile and edit, relations, followers, invitations, posts, comments, reactions |
| Posts | Create, get, comments and replies, reactions (posts and comments) |
| LinkedIn search | Classic people, companies, jobs, posts; Sales Nav people and companies (saved and recent searches); Recruiter; search parameters |
| LinkedIn | Companies, InMail balance, contracts, raw data, Sales Nav lists (`saveLead`), Recruiter projects and pipeline, job postings and applicants |
| Email | Emails, folders, drafts, attachments |
| Webhooks | Sources above |

**Not supported yet** (they keep working through Unipile for accounts not moved yet): calendars, email tracking, email contacts, Instagram, Telegram, X, Messenger, `addApplicantToPipeline`, skill endorsements, post drafts, post targeted audience, replying or reacting to a comment as a company page, deleting a Sales Nav or Recruiter chat, profile edits of `open_to_work`, custom link and picture settings, paid job publishing and its checkpoint, Recruiter session sign-out.

- **Recruiter job postings** (`service: RECRUITER`): get, publish and close a job posting, list its applicants, download an applicant's resume. The same actions work on classic job postings.
- **Recruiter search filters**: `saved_filter`, and a `locale` other than `english` (results come in the seat's own language). `saved_search` runs alone, as saved.

`degree`, `employment_type`, `spoken_languages`, `spotlights`, `tenure_in_company` and `tenure_in_position` are supported on Recruiter Pro seats. On Recruiter Lite, LinkedIn refuses them and the search answers `403 errors/feature_not_subscribed`.
